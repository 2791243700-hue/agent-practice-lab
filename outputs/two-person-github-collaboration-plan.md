## 2. 开始开发前共同确定的契约

B 先提出最小契约 PR，A 根据界面所需信息审阅，合并后双方并行。

- HTTP：/api/v1/me、model-profiles、lessons、attempts、runs、approvals、submissions 等资源的路径、方法、请求与响应，以及错误码。明确哪些操作可能消耗模型额度。
- 字段：lesson_id/version、attempt_id、run_id、call_id、approval_id、submission_id；日期与时间格式、运行状态、live/demo 标记、幂等键。
- SSE：事件序号、事件名、每类 payload、终态、Last-Event-ID 重连方式。统一事件持久化后发送，浏览器重连只补读事件。
- 课程：manifest、intro_file、材料引用、理解题答案结构、规则 ID 和证据引用；课程改版不能改变旧实验。
- 授权：逐次 approve/deny、超时、重复决定、取消后决定的返回行为；显示参数和服务端执行参数保持一致。
- 验收：每项规则的 passed、required、message、evidence_refs；前端展示反馈，后端决定正式通过。

Pydantic 模型为服务端类型来源，导出 contracts/openapi.json；有明确类型的事件模型导出 contracts/events.schema.json。前端类型从契约生成，禁止修改生成文件来绕过不一致。CI 检查导出内容与源模型一致。

contracts/examples/ 提供无敏感信息的成功、失败、等待授权、拒绝、过期、取消和评分不通过样例。A 据此编写前端模拟接口；模拟只用于开发和演示，页面明确标记，不能写入正式课程通过记录。

如需更改字段，提交同一个 PR 更新契约、示例和对应实现。对跨两人文件的修改先约定一名提交者，另一人审阅；不各自维护不同的接口版本。

## 4. 一个 GitHub 仓库的使用方式

1. 确定仓库地址与账号权限。两人各自在自己的机器 clone 同一个仓库。已有仓库先检查现有内容与分支，保留历史。
2. main 保存可运行的已合并版本。每项功能从最新 main 建短期分支，例如 feat/lesson-intro、feat/model-settings、feat/runtime-events、feat/grading。
3. 各自在自己的功能分支提交并 push 到同一远程仓库，随后发 Pull Request。通过 Git 提交与合并统一代码，不在网页上反复上传覆盖整个目录。
4. 对方审阅，检查通过后合并。A 的 PR 重点由 B 检查接口与规则边界，B 的 PR 由 A 检查页面所需字段、错误提示与事件表现。
5. 合并后另一人同步 main 再继续后续功能。功能分支内提交合并产生的冲突修复；不强推 main，也不让两人同时推同一功能分支。

无需长期保留 person-a/person-b 两条大分支；按功能开小 PR，更容易早期发现接口不匹配。

仓库权限允许时设置 main 分支保护：要求 PR、另一人一次审阅、已接入的检查通过；避免配置尚不存在的必需检查使仓库无法合并。CODEOWNERS 待获得双方真实 GitHub 用户名后再配置，不能填写虚构账号。

PR 说明至少包含：完成了什么、接口或课程规则是否变化、验证结果、截图或操作步骤（界面变更时）、尚未验证事项。界面可模拟运行不等于正式实训已验收。

## 5. 合并前检查

- 前端变更：类型检查与构建；涉及学习、授权或恢复流程时运行对应浏览器用例。
- 后端变更：受影响的 pytest；数据库变更验证迁移；权限、评分和状态恢复必须有对应反例。
- 契约变更：重新导出 schema、生成前端类型，验证示例和双方消费方。
- 首版交付：跑完整测试、构建和浏览器流程，并在 Windows 检查启动、停止和重启；CI 测试使用脚本模型，真实模型实测单独记录。
- Git 排除真实 .env（保留 .env.example）、密钥、SQLite、data/、工作区产物、日志、虚拟环境、node_modules、.next 和本地测试缓存。上传前检查暂存区；运行数据需要导出时走应用导出功能，不混入源码仓库。
